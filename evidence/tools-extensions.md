## 架构结论

1. **工具是一套统一合同，执行器独立于工具实现。** Tool 对象暴露 name、inputSchema/outputSchema、isEnabled、isReadOnly、isConcurrencySafe、validateInput、checkPermissions、call、mapToolResultToToolResultBlockParam 等能力；并非每个工具都实现全部可选项。内置工具和 MCP 包装工具进入同一调度/权限/结果路径。[TE-01/07/14]
2. **调度并非任意 Promise.all。** module-745 队列记录 queued/executing/completed；先以 inputSchema.safeParse 的成功数据调用 isConcurrencySafe。未知/抛异常默认为 false。已有执行中任务时，只有当前和全部正在执行任务都 concurrency safe 才可重叠；遇到不安全的排队项会停止向后调度。执行器为各调用派生 abort controller，通过 D6 异步生成器接收执行事件。[TE-01/02]
3. **调用链可概括为** 模型 tool_use → 名称/alias 解析与动态 MCP 等待 → 输入 JSON/schema 与工具 validateInput → PreToolUse hook → 权限决策 HOr → 仅 allow 进入 call → PostToolUse → schema 校验可能改写的输出 → 转 tool_result。拒绝、取消、缺失工具均生成 tool_result 错误，不等于直接抛弃消息。[TE-03..08] 继续追到 HOr→T8r：PreToolUse deny 直接走拒绝；hook allow/ask 仍检查 BT/XHs，deny rule 覆盖 hook allow，ask rule/安全检查/plan mode 可要求回到完整 canUseTool 流程；requireCanUseTool 时 hook allow 也必须调用中央决策。完整 managed policy 优先级未穷尽。[TE-26]
4. **沙箱是执行边界的一层实现，与模型工具授权是不同层。** macOS 后端确实构造 sandbox-exec -p profile 包裹 shell 命令；Linux 确实构造 bwrap 并防 NUL/参数长度超限。沙箱管理器代码同时含文件读写路径限制、网络代理及平台差异。不能据静态代码宣称本机当前会话启用了沙箱，也不能推断每个 MCP 进程都受相同沙箱包裹。[TE-09/10]
5. **MCP 是完整外接工具平面。** module-2110 包含 stdio 子进程 transport、HTTP/SSE/WS/IDE/sdk/claudeai-proxy 路由和 legacy/auto 协议协商；tools/list refresh 使用重试，并有 listChanged refetch 处理。连接状态持有错误计数、activeCallWatchdogs、callsInProgress、pendingElicitations；stdio transport 明确 shell:false、stdout 读缓冲、关闭回收。[TE-11..13] 部分较新协商分支受 feature flag、server denylist 和配置约束，非普遍启用。
6. **MCP 工具不会绕过统一授权。** 上游 JSON Schema 被包装为统一工具 inputJSONSchema；readOnlyHint 参与 isReadOnly 与 isConcurrencySafe，annotations 的 destructiveHint/openWorldHint 也会保留；checkPermissions 可强制 ask 或返回 passthrough 交中央策略处理。并发的 readOnlyHint 是服务端提示，不是静态证明工具无副作用。[TE-14]
7. **CLI 也能作为 MCP server。** module-2484 tools/list handler 动态列出可服务工具，并在策略变动后发送工具列表变更通知；tools/call 路径进行 isEnabled、schema、validateInput、checkPlainCall，再调用 T.call。这里不是对话模型代理：它把内部工具作为 MCP 服务暴露，使用机械化的 toolUseContext；是否启动此模式未知。[TE-15/16]
8. **Plugin 是组合扩展包，不只是提示词。** manifest 优先 `.claude-plugin/plugin.json` 再 `plugin.json`。组件路径包含 commands、agents、skills、outputStyles、themes、workflows、monitors；文件组件有 mcpServers、lspServers、hooks。实际 P$ 重载函数清缓存并刷新 config、并发获取命令/技能/agent 定义，加载 MCP/LSP、更新状态、再注册 hooks。插件加载错误独立收集，因此是可部分失败的扩展系统。[TE-17/18]
9. **Hooks 为生命周期中间件，有信任与并发注册控制。** Q9 以 hookRegistrationEpoch/hookSwapEpoch 防止较旧注册覆盖新版，并将 hook modules 挂在 workspace trust 门禁之后。事件集合有 PreToolUse、PermissionRequest、PostToolUse、SubagentStart/Stop、TaskCreated/Completed、WorktreeCreate/Remove 等。结果规范化将 PreToolUse block 表达为 permissionDecision:deny；超时是否 fail closed 有参数和事件条件，不能一概声称所有 hook 失败都拒绝执行。[TE-19/20]
10. **Skill 与插件相关但职责不同。** SKILL.md 的元数据作为常驻描述，正文在调用时引入；module-2233 的插件 token 估算明确把 description/whenToUse 生成 alwaysOn，content.trim() 作为 onInvoke。这证明上下文分层设计。已继续追到真正插件 Skill 链：TXo 枚举 enabled plugin 的 skillsPath/skillsPaths，Hje 以 realpath 去重，并跳过已被用户 skills directory loader 提供的同一路径；Mq 将 frontmatter 转成 prompt 对象，解析 allowed-tools/model/effort/context:fork/agent/background/disable-model-invocation/user-invocable 等，并以 getPromptForCommand 在调用时展开正文、参数和变量。完整用户/项目 skill 优先级仍未知。[TE-25/27/28]
11. **LSP 是语义代码能力适配器，IDE 是另一条集成通道。** LSP tool 把用户 1-based line/character 转为 protocol 0-based，映射 goToDefinition/findReferences/hover/documentSymbol/workspaceSymbol/goToImplementation/call hierarchy 请求。插件 LSP 配置来源 .lsp.json 和 manifest.lspServers，带 schema 与相对路径验证。IDE 的连接经 SSE/WS MCP 并发 ide_connected 通知；二者不应混成同一个服务。[TE-21..24]
